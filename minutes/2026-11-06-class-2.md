### 2. How Tools Are Offered to a Model

The instructor explained that a model can only respond with text until it is offered tools, and showed how a Runvil prompt offers tool packs with `tools.offer`.

- One participant had read the opening section of the harness document (the one-paragraph and five-paragraph versions) and had not yet read the detailed parts.
- A tool has a name, a description that tells the model what it does, and parameters that say what to pass in. The tool catalog is sent along with each conversation.
- Larger models can use more tools, and offering too many (500 was the example) confuses any model. The smallest models may handle only about 3 to 5 tools, and models of roughly 3 to 9 billion parameters perhaps 5 to 8, so controlling which tools a small model sees matters.
- The chat prompt offers three required packs: user input, standard tools (read, write, grep, list a directory, delete, string replace, all on the virtual file system), and web (search and fetch). It also offers any other packs the host loaded.
- The user input pack is required because without it nothing can be typed to the model.
- The instructor said the prompt's explicit offer of the user input tool is probably a bug (AMB-5).
- Web search costs money. Sites such as Google block bots because they want ads seen by humans, so anyone who wants web search needs an API key for a paid service such as Brave.

### 3. API Keys: Gateway or Harness

A participant explained that the gateway holds all API keys, and the instructor and that participant discussed whether keys belong in the gateway or the harness without changing the design.

- The gateway keeps keys in an environment file loaded at startup. Keys are added through the settings UI, or by editing the environment file for hosted or persistent deployments. The gateway works out which key each request needs.
- The instructor asked why web search and inference share one component. The participant said it depends on the usage model: a key shared by an organization on a server fits the gateway, while individual keys might fit the harness.
- The instructor gave two reasons for the gateway. It acts as a security envelope with every key in one process, which reduces the attack surface. Several programs (two workshop copies in different workspaces, or a prompt that runs hourly to check email) can use web search without each holding the key. The participant agreed that having keys in one place is also true.

### 4. Engine and Harness Separation

The instructor explained that the Runvil engine is kept to the minimum needed to deliver the prompting language so it can eventually be finished, and that everything else belongs to the harness or to plug-ins.

- A participant summarized the harness document as separating the model's requests from its actions, which matches the engine and harness split in Runvil. He had also read about differences between cloud provider endpoints.
- The engine is everything needed to deliver the language, such that removing any piece breaks it. The harness is everything needed for the engine to interact with the outside world, such that removing any piece breaks it. User input, web, and standard tools are plug-ins outside the harness. A harness without them can only talk to the model.
- The instructor said there are two reasons for the split and described these (AMB-6): agentic workflows work better with small, isolated pieces because large interconnected ones confuse the model and are harder to audit, and a minimal engine means finite tests and a point at which the engine can be called finished.
- New features go into the harness, plug-ins, Lua preludes [?], or the workshop UI instead of the engine. Once the harness supports plug-ins properly, the same applies to the harness.
- Others may write their own harnesses, for example for a phone or other small device that needs only a few built-ins. The instructor is not opposed.

### 5. Unfinished Plug-in System and the VFS API

The instructor listed what is missing from the plug-in system and said plug-ins must reach the virtual file system through an exported API.

- Plug-ins do not exist yet beyond a small API in a plug-in API crate. No DLLs are built, no directory is scanned and loaded, and plug-ins cannot yet register packs.
- A plug-in is code in a shared library (or linked in [?]) that provides zero or more packs. A pack has a name and provides zero or more tools. User input, STD, and web are packs that currently come from built-in plug-ins. A prompt can require a pack from an external DLL, for example a Bashkit pack, and then runs only if that plug-in is available.
- Plug-in file IO has to go through the virtual file system, otherwise plug-in tools cannot see mounted virtual files such as the store. The instructor kept the VFS API small, so exporting it is not difficult.
- The API reaches a plug-in through an Access object. Operations named: append, close, copy, exists, list, glob, read, a partial read of a range of a file, remove, rename, and write.

### 8. Determinism and the Model's Recommendation

The instructor explained that the VFS exists to keep every run deterministic through a claims table, and the model's answer on offering both APIs was not to offer both and to ship the synchronous one first.

- The VFS detects nondeterministic behavior by sub-agents, such as two appending to one file at once, or one reading while another writes, and stops the prompt with a nondeterminism error. About 80 percent of the VFS module is the ordering algorithm behind this.
- Each chain records claims for files it reads, writes, or checks, and every new operation is compared against the claims table for conflicts.
- A participant suggested that git work trees for agents could be a workaround. The instructor answered with a fan-out example in which ten research sub-agents write to separate virtual files that must later be combined, and said whether the combination is safe depends on the algorithm.
- The model's advice was: do not offer both, ship synchronous now, leave room for async as an additive surface, and note that the engine chose sync on purpose for determinism.
- A participant said that introducing async means choosing how to preserve determinism, which is a hard problem.
- The instructor asked what several more terms in the model's answer mean ("abort merges the child immediately", a mutex box, VFS Access being only Send and not Sync). A participant described them as Rust traits about communicating across threads (AMB-9).
- The instructor said synchronous appeals to him because it can be done right away, it brings plug-ins such as Bashkit, and it lets people work separately so the team can scale. He is not comfortable yet because he cannot follow the model's explanation, and he said a consequential decision should not be made casually.

### 9. Access, Borrowing, and Cancellation

The instructor explained how Access objects, borrowing, and revocation on cancel work in the VFS, and participants raised practical points on whether async matters given inference latency.

- The VFS is shared by every prompt in the workshop. To use it a caller must be handed an Access that contains the chain's unique ID, which lets the VFS track who is doing what even across prompts. Two prompts touching the same file can conflict and are stopped.
- A plug-in receives the Access as a borrow, so it cannot pass it on or create its own. The instructor said this lets the host make stronger guarantees about how the Access is used.
- When a plug-in returns or drops the Access, its claims on files are released. On cancel the Access is revoked, and the plug-in must handle the error the next time it uses it. The instructor chose this so that pressing stop and exiting the app are immediate and do not require unwinding many plug-ins.
- A participant read the model's text on worker threads and ending the Access on cancel as describing race conditions.
- The same participant said inference takes orders of magnitude longer than VFS operations, especially over a network or with a slow local model, and his point was cut off. The instructor answered with a zip tool compressing a 1 gigabyte file, which would block every other prompt, and the participant agreed it was a good point.
- The instructor listed costs of async from the model's answer, including in-flight work after abort and that a blocking system call cannot be canceled by dropping a future.
- The same participant suggested thinking about whether something is already accessing a file instead of sync versus async (AMB-9). The instructor said the system already works that way.
