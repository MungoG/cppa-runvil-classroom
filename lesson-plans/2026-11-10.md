# Lesson Plan: 2026-11-10

## The most important thing

Everyone's job is to learn. If you are learning, you are doing your job. It does not matter if you are slow, and it does not matter if you are struggling. Struggling is probably a good thing. It means you have found something you do not know, which is great.

Be judicious about when you use the LLM. Every time you use it, you take a learning opportunity away from yourself.

1. First, see if you can avoid it.
2. If you are having trouble avoiding it, use it a little. Ask a light question.
3. Try not to ask a question that just produces the entire answer.
4. If you get completely stuck, ask.

Write things yourself. If your version is a few sentences and the AI would produce pages, your version is still better, because writing those sentences is how you learn. Putting the information into your own words is what creates the lasting memory.

## Push your work every day

Push your work to your directory under `students/` every day. It does not matter if it works, if it is incomplete, or what condition it is in. The instructor wants to see it change from one day to the next, and if it is not working we can still talk about it. Open the pull request from your fork and merge it yourself.

## Today's work

1. **Run your prompt.** Run the [tools-public](https://github.com/cppalliance/tools-public) prompt you chose, in Cursor, as it is, before you convert anything. If you have not chosen one, pick from the Tools table in the [2026-11-06 lesson plan](2026-11-06.md).
2. **Plan a Host for it.** A Host is the application that runs a prompt through the Runvil Harness. Workshop is one. Yours might be a small web server or a command-line wrapper. Decide what kind fits your prompt and write it down. No code is needed today.
3. **Build and run vibelight.** [vibelight](https://github.com/cppalliance/vibelight) writes an outline of every Rust crate in a repository: the types, traits, functions, and comments, with no function bodies. Everyone needs to know how to use it. Clone it next to `runvil`, run `cargo install --path .` in its folder, then run `vibelight` at the root of `runvil`, `runvil-gateway`, and `runvil-plugin-api`. Open `.vibelight/html/index.html` in each and look around.
4. **Study the `runvil` crate.** It is the one crate a Host depends on. Open its page in the vibelight HTML and start working out how it fits together. The [`plan/`](https://github.com/cppalliance/runvil/tree/master/plan) and [`vibe/`](https://github.com/cppalliance/runvil/tree/master/vibe) files in the `runvil` repository explain the designs, and newer ones are more reliable than older ones. A good first read is the [Lua syntax section of the run inbox plan](https://github.com/cppalliance/runvil/blob/master/plan/2026-11-08-2-run-inbox-user-pack.plan.md#lua-syntax). Plans keep the crate names from the day they were written, and three changed today: `harness` is now `runvil`, the old `runvil` is now `runvil-engine`, and the old `runvil-engine` is now `runvil-runtime`.
5. **Optional: install Unsloth Studio.** [Unsloth Studio](https://github.com/unslothai/unsloth) is a free app for running models on your own machine, and it does many of the things we want to do. Try a model of around 3 billion parameters on your video card.

## Standing order: iterate on your extraction prompt

If you have run your extraction prompt on a transcript, read your own output. Then, in front of the class, say what you like about it, what you do not like, and how it might be improved. Afterward, improve the prompt, run it again, and push the result.

This is a standing order. It can be this class or the next one, and it does not end. The idea is to get into the loop of making a prompt better, and to look at each other's outputs. A good one to read is [Harry Bott's class 1 output](../students/bott/outputs/2026-11-06-class-1.md).
