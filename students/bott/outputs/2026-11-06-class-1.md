## Summary

Nearly all of the judgment in this meeting is Vinnie's. He consistently optimizes for transfer to a learner as the finish line, for owning the layers where his judgment differs from a vendor's, and for cheap, fast iteration: self-merged pull requests, record-and-replay, prompts that run quickly, and classes that end on time. He consistently refuses three things: work that has already been solved elsewhere (deployment, self-hosting, privacy), committing to answers or evaluation criteria before the team has tried things, and letting AI write the artifacts people are supposed to learn from. The biggest gap is a reflexive one. Vinnie says the team's job is to pull undocumented design knowledge out of him, yet the moments where that knowledge was asked for directly (what a good extraction looks like, how the gateway extensions work, where captured knowledge lives) were answered with "I have no idea," "it's not that complicated," or "isn't it obvious?"

## Concepts

- **C1 Tacit knowledge:** experiences, skills, and judgment someone acquired by doing something for a long time, which aren't written down as rules (3:29).
- **C2 Succession problem:** when someone who knows something leaves, the knowledge leaves with them unless it was captured (26:12).
- **C3 Knowledge capture pipeline:** interview, transcript, extraction into experiences and principles, storage, then an adaptive learning program that transfers the knowledge to another person (6:28, 19:10, 26:12).
- **C4 Transcript:** the recorded text of a session, saved in the repository so it can be mined later (17:20).
- **C5 Story walk and variations:** the interviewer locks onto a story, walks through it with questions, then asks "what if" variations once the story runs out (34:46, 35:16). The full set of "seven ways" is not explained, see G11.
- **C6 Extraction prompt:** a prompt that turns a transcript into something actionable (19:10).
- **C7 Scribe:** an existing tool that turns minutes into a summary document (19:29, 19:46).
- **C8 Design principles:** not explained, see G1.
- **C9 Adaptive learning program (pedagogue):** a tutor that adjusts its pace to the learner, speeding up for fast learners and backing off after mistakes (6:28, 7:33).
- **C10 Mentograph / mentographist:** an interview tool that finds a story, walks it, and explores variations (34:15). Its relationship to Toctron is not explained, see G5.
- **C11 Runville:** a prompting language in which the prompt author decides which part of the system holds authority (11:46).
- **C12 Orchestration authority:** which party (Lua code, the model, or a classifier) decides what happens next in a prompt (11:46, 12:05).
- **C13 Classifier:** not explained, see G9.
- **C14 Ad hoc tool:** a tool written inside the prompt and offered to the model (12:48).
- **C15 Agent harness:** the program that packages the chat history and new input, sends it through the gateway to the model, and displays the response (41:58).
- **C16 Messages:** the growing stack of messages that Runville maintains and sends to the model in full on every turn (43:02).
- **C17 Compaction ("AI lobotomy"):** shrinking the message stack when it gets too big so there's room again (43:19).
- **C18 Tool loop:** not explained, see G18.
- **C19 Workshop:** an IDE that understands Runville, with breakpoints and inspection of the prompt's state, store, files, and variables (14:51).
- **C20 Record and replay:** recording every tool call, Lua function call, and model interaction during a run so it can be replayed up to a breakpoint without new inference (15:46).
- **C21 Gateway:** an inference endpoint that speaks a generic format and translates it into each provider's proprietary API (37:38, 38:15).
- **C22 Signed and encrypted thinking blocks:** provider-attached signatures or encryption on thinking output that must be sent back unchanged (38:52, 39:42).
- **C23 Lua side and Rust side:** prompt code in Lua sees the messages object, which is backed by a Rust struct that can carry data Lua can't see (44:22, 44:39). Why that data is hidden is not explained, see G12.

## Teaching units

### H1. Capture is not finished until the knowledge transfers

- **Rule:** When designing a knowledge capture effort, treat it as finished only when another person has learned the knowledge, not when it has been stored, because the whole point of capturing knowledge is to transmit it to another individual.
- **Domain:** teaching and learning
- **Tier:** STATED
- **Speaker:** Vinnie
- **Evidence:** "the pipeline starts with the capture and it ends when it's transferred to another person" [26:12]; "The whole point of capturing the knowledge is so that you can transmit it to another individual" [26:12]; "at all times, our goal will be to present the information in a way that where people can learn it" [20:59]
- **Prerequisites:** C1, C2, C3
- **Conflicts with:** none
- **Practice scenario:** A hospital records interviews with a retiring charge nurse, indexes them in a searchable archive, and reports the project complete. A new charge nurse starts next month.
- **Expected reasoning:** The project isn't done. Capture ends at transfer, so the next step is to build something the new nurse can actually learn from and to check that she did.
- **Likely wrong answer:** Treating distribution tooling or a searchable store as the finish line (observed at 26:06, where Mateo asks about tools to distribute knowledge across the enterprise, and is redirected to person-to-person transfer, which he restates at 28:06).
- **Open gaps:** none

### H2. Get design rationale from the designer, not from the code

- **Rule:** When a system's designer made decisions that were never written down, extract those decisions from the designer before trying to infer them from the code, because without them no one can tell whether the code is right or something is missing, and the code alone will overwhelm you.
- **Domain:** team process
- **Tier:** STATED
- **Speaker:** Vinnie
- **Evidence:** "They're not written down" [18:39]; "no one can tell if the code is doing the right thing" [18:39]; "you're not gonna find this by looking in the rust code, that's just gonna overwhelm you" [40:59]
- **Prerequisites:** C1
- **Conflicts with:** none
- **Practice scenario:** You inherit a billing service. The engineer who designed it is moving to another team in two weeks and is still reachable.
- **Expected reasoning:** Spend the two weeks drawing out why the designer made the choices they made. The code will still be there afterwards; the designer's undocumented reasoning will not.
- **Likely wrong answer:** Spending the two weeks reading the code alone and planning to ask questions later (predicted).
- **Open gaps:** none

### H4. Interview for stories, then probe with what-ifs

- **Rule:** When interviewing someone to capture their judgment, steer them into a specific story, walk through it, and then ask what-if variations, because the variations are the most revealing part: they show how the person thinks.
- **Domain:** teaching and learning
- **Tier:** STATED
- **Speaker:** Vinnie
- **Evidence:** "you try to get them to tell a story" [34:15]; "then it performs what's called a story walk" [34:46]; "those what ifs, and like those modifications to the story is the most revealing aspect because it it explains how the person thinks" [35:16]
- **Prerequisites:** C1, C5, C10
- **Conflicts with:** none
- **Practice scenario:** You're interviewing a senior support engineer about how she decides when to escalate a ticket to engineering.
- **Expected reasoning:** Ask for one specific escalation she remembers, walk through it step by step, and once it's exhausted ask something like "What if the customer had been a free-tier user?" Her answer to the variation reveals the rule she's using.
- **Likely wrong answer:** Asking "What are your rules for escalating?" and recording the generic answer (predicted).
