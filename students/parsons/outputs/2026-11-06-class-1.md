# Design Ledger: 2026-11-06-class-1.md

This session defines how Runvil separates orchestration, inference, and classification authority across Lua code and the model, why Runvil Workshop replaces vendor-controlled context enrichment with prompt-specific compaction and deterministic record-and-replay, and how Gateway bridges a generic OpenAI-style endpoint to proprietary frontier-model requirements like signed and encrypted thinking blocks. It also introduces the Knowledge Capture Corporation's three commercial products built on Runvil and frames the classroom itself as the live prototype of the capture-to-transfer pipeline.

## 1. Runvil Architecture & Design Decisions

1. **Per-section orchestration authority** [`Language`] `[11:46]` `[12:05]` - **Decision:** The prompt author explicitly assigns authority per prompt or per section, choosing whether Lua code or the model orchestrates execution, while the model starts with inference authority and classification can optionally be delegated to a classifier. **Rationale:** Gives the author complete control over execution flow, such as using Lua orchestration to gather documents and links first and then handing orchestration to the model over that curated context.
2. **Section-scoped and ad hoc tools** [`Language`] `[12:05]` `[12:48]` - **Decision:** A prompt author can grant different subsets of tools to the model in different sections of a prompt and can define custom ad hoc tools inline for the model to call. **Rationale:** Prevents exposing every tool globally when a section only permits specific actions.
3. **Author-controlled context enrichment and compaction** [`Workshop`] `[13:47]` `[14:21]` - **Decision:** Runvil Workshop keeps context enrichment and compaction retention policies under the prompt author's control rather than routing prompts through a third-party IDE server. **Rationale:** Different prompts need different memory policies; for example, `mentograph` may only need to retain the last two stories across compactions to keep token costs down.
4. **Prompt state inspection and breakpoints** [`Workshop`] `[14:51]` - **Decision:** Workshop integrates directly with Runvil so an author can launch a prompt via keyboard shortcut, pause at a breakpoint, inspect the store, virtual files, and variables, edit the prompt, and rerun. **Rationale:** Treats prompts as debuggable programs with observable state rather than opaque chat sessions.
5. **Deterministic record-and-replay** [`Engine` / `Workshop`] `[15:21]` `[15:46]` `[16:15]` - **Decision:** Runvil records every tool call, Lua function call, and model interaction during execution so a rerun can replay recorded effects right up to a breakpoint without repeating upstream inference. **Rationale:** Multi-step research pipelines can take 20 minutes to 2 hours to crawl and extract web data; fixing a hallucinating step 7 must not require re-executing steps 1 through 6.
6. **Custom harness presentation surfaces** [`Harness`] `[24:33]` `[27:13]` `[27:43]` - **Decision:** Runvil prompts can be wrapped in custom harnesses such as a CLI wrapper or a web server that renders textbook-style pages and interactive multiple-choice quizzes triggered via model tool calls. **Rationale:** Decouples the underlying teaching or interviewing prompt from terminal-only chat interfaces.
7. **Gateway generic protocol with minimal extensions** [`Gateway`] `[37:38]` `[38:15]` `[40:04]` `[40:22]` - **Decision:** Gateway exposes a generic OpenAI-style messages-and-tools endpoint plus a minimal set of extensions used by the Runvil engine, and translates those requests into each frontier provider's proprietary API. **Rationale:** Allows full access to provider-specific frontier capabilities (Claude, ChatGPT) without breaking compatibility for generic clients using the Gateway.
8. **Anthropic cryptographic thinking-block preservation** [`Gateway` / `Engine`] `[38:52]` `[39:08]` - **Decision:** When interacting with Anthropic endpoints, Gateway and Engine must capture the cryptographic signature attached to each thinking block and return historical thinking blocks unedited, unremoved, and in exact order. **Rationale:** Anthropic signs thinking blocks to prevent distillation tampering; mutating, dropping, or reordering any past thinking block invalidates the hash chain, evicts the prompt cache, and fails the request with an HTTP error.
9. **OpenAI encrypted thinking-block preservation** [`Gateway` / `Engine`] `[39:42]` - **Decision:** When interacting with OpenAI endpoints, redacted and encrypted thinking blocks must be stored as opaque bit blobs and echoed back verbatim on subsequent turns. **Rationale:** OpenAI rejects any request where encrypted thinking payloads have been altered or omitted.
10. **Streamed chat responses to Workshop** [`Gateway` / `Harness`] `[41:58]` - **Decision:** The harness packages chat history and new user input, sends them through Gateway to the model, and uses a streaming extension to render tokens in Workshop as they arrive. **Rationale:** Waiting for a full completion before displaying text feels sluggish to the user.
11. **Append-only `messages` stack and builder loop** [`Language` / `Engine`] `[42:36]` `[43:02]` `[43:58]` - **Decision:** Runvil maintains the conversation (including the background system prompt) in a growing `messages` object; the chat prompt appends new user input via a builder and invokes the tool loop, sending the full stack on each turn until size limits trigger compaction. **Rationale:** Keeps the full conversational context explicit per turn while standardizing how user input enters the tool loop.
12. **Rust-backed `messages` struct with hidden metadata** [`Engine`] `[44:22]` `[44:39]` - **Decision:** The Lua-visible `messages` object is backed by a Rust struct that carries additional fields invisible to Lua, including the tool catalog and provider-specific gateway metadata. **Rationale:** Lets the Engine pass protocol-level data (such as tool definitions and thinking signatures) to Gateway without cluttering the Lua prompt surface.

## 2. Product & Pipeline Mechanics

13. **Open-source core vs. commercial knowledge layer** [`Business`] `[5:50]` `[8:03]` `[11:08]` `[29:51]` - **Mechanism:** Runvil and Runvil Workshop remain permanently open source, while the Knowledge Capture Corporation operates as a for-profit company (targeting acquisition or IPO) selling three products built on Runvil. **Rationale:** Separates the open developer platform from the revenue-generating knowledge capture and learning products.
14. **Product 1: On-site enterprise knowledge capture** [`Product`] `[5:50]` `[6:28]` - **Mechanism:** Deployed as a Docker container inside a customer's network or as a cloud subscription; human or AI-assisted interviews (`Talktron` / `mentograph`) produce transcripts, extraction prompts distill experiences and principles into a database, and an adaptive learning program (`pedagogue`) trains employees. **Rationale:** Solves the organizational succession problem (`[26:12]`) when experienced staff leave.
15. **Adaptive tutoring rules in `pedagogue`** [`Product`] `[6:53]` `[7:14]` `[7:33]` `[27:43]` - **Mechanism:** The tutor adjusts pacing to the individual learner, never reveals the answer directly, gates progression with tool-call quizzes, and backs off to a simpler topic to rebuild confidence whenever a student makes two or three consecutive mistakes. **Rationale:** Embeds proven pedagogical techniques directly into the tutoring prompt and harness so content authors do not have to build adaptive logic themselves (`[10:12]`).
16. **Product 2: Autobiographical virtual confidant** [`Product`] `[8:03]` `[8:43]` `[9:16]` - **Mechanism:** Uses the same interview-and-extraction pipeline for personal or executive history (for example, a grandparent or a retiring CEO), creating a cloud-hosted or downloadable AI persona that answers third-person questions about the subject. **Rationale:** Deliberately framed as a trusted confidant who knows the person rather than a first-person virtual simulation, which the designer rejects as uncanny and weird (`[8:43]`).
17. **Product 3: Interactive knowledge marketplace** [`Product`] `[9:42]` `[10:12]` - **Mechanism:** A YouTube-style marketplace where thumbnails launch interactive, adaptive learning programs rendered as avatars, textbooks, or slideshows; subscribers pay for access and creators are paid in proportion to program popularity. **Rationale:** Aligns creator compensation with effective teaching while offloading adaptive delivery to the platform.
18. **Randomized 10% free access for ungameable ratings** [`Product`] `[10:42]` - **Mechanism:** Subscribers receive a random 10% of marketplace learning programs for free on the condition that they leave a rating and comment afterward. **Rationale:** Guarantees a steady stream of reviews that are randomly distributed across programs and resistant to rating manipulation.
19. **Three-phase `mentograph` story elicitation** [`Pipeline`] `[34:15]` `[34:46]` `[35:16]` `[35:40]` - **Mechanism:** Based on the SAGE paper, `mentograph` chats openly until it locks onto a specific story, conducts a step-by-step story walk until narrative energy drops, and then probes with seven types of counterfactual what-if variations. **Rationale:** Counterfactual modifications force the subject to adapt their story to new conditions, which exposes how they actually think and decide.
20. **Classroom as live product prototype** [`Pipeline`] `[18:19]` `[18:39]` `[28:23]` `[29:15]` - **Mechanism:** Recording Vinnie's sessions, transcribing them, and having students write extraction prompts to recover his undocumented 2 a.m. Runvil design decisions enacts the exact capture-to-transfer pipeline the company plans to sell. **Rationale:** Produces both internal Runvil documentation and the empirical case study backing the commercial product.
21. **Hand-written prompt ports from `tools-public`** [`Workflow`] `[21:48]` `[23:45]` `[24:13]` - **Mechanism:** Each student selects an existing prompt from `tools-public` (Will on `mentograph`, Jason and Glenn on `Agora`, Greg on `coc-blocker`) and ports it to Runvil by hand in small weekly increments without AI code generation. **Rationale:** Writing Runvil prompts by hand teaches the language deeply and surfaces missing Engine features that steer engineering priorities.
22. **Two-track meeting structure** [`Workflow`] `[24:51]` - **Mechanism:** Alternates instructor-led teaching sessions with instructor-free student huddles where the team compares prompts, critiques what worked or failed, and formulates follow-up questions. **Rationale:** Removes instructor influence so the team can evaluate progress candidly.

## 3. Engineering & Teaching Principles

23. **Knowledge capture ends at transfer, not storage** `[20:59]` `[26:12]` `[28:23]` (`stated`, Vinnie) - **When** designing a knowledge capture system or evaluating its output, **do** treat the pipeline as complete only when another person has learned the knowledge through an instruction manual or adaptive tutor, **because** stored transcripts or enterprise distribution tools have no value unless the capability transfers to a human replacement.
24. **Extract teachable decisions, not meeting statements** `[19:46]` `[46:06]` (`stated`, Vinnie) - **When** building an extraction prompt over a transcript, **do** discard administrative statements and chronological summaries and prioritize domain-specific design decisions and principles first, **because** generic summaries (`scribe`) record what was said without teaching how to build or decide.
25. **Keep extraction prompts transcript-only and fast** `[46:30]` `[46:37]` (`stated`, Vinnie) - **When** designing a reusable transcript extraction prompt, **do** restrict its input strictly to the transcript without crawling source code or external files, **because** pulling in outside sources sends the prompt into the weeds and makes iteration slow.
26. **Mine design rationale from the architect before reading code** `[18:39]` `[40:59]` (`stated`, Vinnie) - **When** onboarding onto a system whose design choices were never written down, **do** interview the designer and extract their tacit rationale before diving into the implementation, **because** reading raw Rust source code alone overwhelms newcomers and cannot reveal whether behavior is intentional or missing.
27. **Trust newer research reports over older ones** `[36:13]` `[36:33]` (`stated`, Vinnie) - **When** navigating an accumulated design repository (`runvil-design`) containing historical artifacts, **do** weight documents by recency (preferring last week's report over July's), **because** older reports go stale as the architecture evolves.
28. **Delegate solved commodity infrastructure to partners** `[31:52]` `[32:10]` (`stated`, Vinnie) - **When** scoping engineering work for a new product, **do** focus strictly on the novel core problem (capture, `mentograph`, `pedagogue`, avatars) and defer commodity concerns like cloud deployment and private enterprise self-hosting to a future equity partner, **because** commodity infrastructure has already been solved many times and turns core engineering time into busywork.
29. **Lead with exciting outputs before showing source** `[2:28]` `[22:52]` `[23:02]` `[23:09]` (`stated` and `demonstrated`, Vinnie) - **When** introducing newcomers to a system or motivating a team, **do** start with the most exciting end result (such as the rendered Agora Reddit-style output page) and work backward, **because** seeing the outcome builds motivation whereas raw prompt code is just a computer program.
30. **Remove review bottlenecks via CLI self-merge** `[20:59]` `[45:33]` (`stated`, Vinnie) - **When** iterating on student prompts and classroom artifacts, **do** grant everyone write access to open and merge their own pull requests from the command line, **because** waiting on central review slows down daily experimentation.
31. **Gate technical detail by audience readiness** `[40:59]` `[42:36]` `[42:56]` (`demonstrated`, Vinnie) - **When** explaining a core architectural mechanism to a mixed-experience group, **do** establish the top-level mental model first (`messages` stack) and set aside secondary details (background `chat.md` system prompt contents, raw Rust internals), **because** front-loading every detail overwhelms learners before the core model clicks.

## 4. Teachable Mental Models

32. **One generic harness explains every agent tool** `[4:09]` `[4:27]` `[41:58]` - An agent harness is the outer loop that packages the conversation history (`messages`), system prompt, tool catalog, and new user input, sends the bundle through Gateway to the model, executes tool calls in a loop, and streams the reply back to the UI. Understanding this single loop explains how Cursor, Claude Code, ChatGPT web, and Runvil all operate.
33. **Compaction as "AI lobotomy" with custom retention** `[14:21]` `[43:02]` `[43:19]` - Because the entire `messages` stack is sent on every turn, the context eventually fills up and must be compacted ("the AI lobotomy"). Instead of a one-size-fits-all summary that forgets critical state or wastes tokens, Runvil lets each prompt define what survives compaction (such as keeping only the last two stories in an interview prompt).
34. **10-step pipeline debugging with record-and-replay** `[15:21]` `[15:46]` `[16:15]` - If steps 1 through 6 of a 10-step web-research prompt take 30 to 120 minutes of network fetches and inference and step 7 starts hallucinating, record-and-replay replays the logged tool calls, Lua calls, and model responses up to the breakpoint before step 7 so the author can iterate on step 7 instantaneously against frozen upstream state.
35. **Cryptographic thinking chains as tamper-evident seals** `[38:52]` `[39:08]` `[39:42]` - Frontier providers protect their reasoning traces against distillation: Anthropic attaches a cryptographic hash signature to each thinking block, and OpenAI returns encrypted bit blobs. The client must treat historical thinking blocks as an immutable, ordered chain; editing or dropping a link invalidates the signature, drops the prompt cache, and causes an HTTP error.
36. **Two-sided `messages` object (Lua view vs. Rust struct)** `[43:58]` `[44:22]` `[44:39]` - To the Lua prompt author, `messages` looks like a simple builder where user text is appended before calling the tool loop. Under the hood, `messages` is a Rust struct carrying hidden cargo (such as the active tool catalog and provider-specific metadata) that Lua cannot see or accidentally corrupt, which the Engine forwards to Gateway.
