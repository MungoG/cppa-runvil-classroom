# Design Ledger: 2026-11-06-class-2.md

This session establishes the architectural boundary between the Runvil Engine, the Harness, and external Plug-in tool packs, explains how the shared Virtual File System (VFS) enforces deterministic execution across concurrent chains and prompts via vended `Access` borrows and a claims table, and examines whether the VFS `Access` API exported across the DLL boundary should be synchronous, asynchronous, or dual-surface.

## 1. Runvil Architecture & Design Decisions

1. **Tool catalog and model parameter scaling** [`Language` / `Harness`] `[5:06]` `[5:22]` `[6:02]` `[6:19]` `[6:45]` - **Decision:** A bare model can only exchange text, so the harness sends a tool catalog (name, description, parameters) with the conversation, and prompts explicitly control visible tools via `tools.offer`. **Rationale:** Tool capacity scales with model size: offering 500 tools confuses even frontier models, while small 3B to 9B parameter models reliably handle only 3 to 8 tools at a time.
2. **Required tool packs in the Workshop chat prompt** [`Language` / `Plug-ins`] `[7:14]` `[7:38]` `[7:55]` `[8:12]` - **Decision:** The Workshop chat agent requires three core tool packs via `tools.offer` - `user_input` (receiving user messages), `std` (file read, write, grep, list, delete, string-replace on the VFS), and `web` (search and fetch) - plus any additional packs loaded by the host. **Rationale:** Without `user_input` a user cannot type to the agent, and grouping capabilities into named packs keeps tool provisioning modular.
3. **Gateway API key sequestration** [`Gateway`] `[8:47]` `[9:45]` `[11:23]` `[11:40]` - **Decision:** Paid provider and web-search API keys (such as Brave search keys) are stored in a Gateway environment file configured manually or through the settings UI, loaded at startup, and attached to outbound requests by Gateway rather than by Workshop or individual harnesses. **Rationale:** Concentrates secrets in a single process with a smaller attack surface and allows multiple Workshop workspaces or scheduled background prompts to share web search and inference without duplicating keys.
4. **Irreducible Engine vs. Harness separation** [`Engine` / `Harness`] `[13:05]` `[13:45]` `[14:02]` `[14:21]` `[14:57]` - **Decision:** The Engine contains only the minimal code required to deliver the Runvil prompting language (removing any piece breaks the language), and the Harness sits on top as the minimal layer required for the Engine to talk to the outside world (removing any piece breaks external interaction). **Rationale:** Keeps component scope and test suites finite so both Engine and Harness can reach a finished state where new capabilities are added only via plug-ins, Lua preludes, or Workshop UI (`[15:15]`, `[15:38]`).
5. **Tools externalized as Plug-ins outside the Harness** [`Harness` / `Plug-ins`] `[14:21]` `[14:44]` `[15:59]` - **Decision:** All tool packs (`user_input`, `std`, `web`, `bashkit`) live outside the core Harness as plug-ins; a naked Harness can converse with a model over text but cannot execute tool calls. **Rationale:** Allows alternative lightweight harnesses (for example, a mobile phone harness with a couple of built-ins and no dynamic plug-in loader) to run Runvil prompts without carrying unused infrastructure.
6. **Plug-in DLLs, Packs, and `uses` declarations** [`Plug-ins`] `[17:29]` `[17:48]` `[18:06]` `[18:23]` - **Decision:** A plug-in is a dynamically loaded shared library (DLL) or statically linked module that registers zero or more named packs, where each pack provides zero or more tools; a prompt declaring `uses.bashkit` can execute only when a plug-in providing the `bashkit` pack is loaded. **Rationale:** Decouples prompt dependencies from core Engine/Harness builds and lets team members develop tool packs independently (`[36:19]`, `[36:34]`).
7. **Mandatory VFS routing for plug-in file I/O** [`VFS` / `Plug-ins`] `[18:55]` `[19:17]` - **Decision:** Plug-in tools must perform all file I/O through the exported Runvil Virtual File System (VFS) API rather than direct OS filesystem calls. **Rationale:** Direct OS calls bypass mounted virtual files and cannot see the prompt's virtual store.
8. **Minimal `Access` file operation surface** [`VFS`] `[19:17]` `[20:10]` `[20:27]` `[20:44]` - **Decision:** The Engine hands each plug-in tool call an `Access` object exposing a compact set of file primitives: `append`, `close`, `copy`, `exists`, `list`, `glob`, `read`, partial range-read, `remove`, `rename`, and `write`. **Rationale:** Keeping the VFS API surface intentionally small makes it practical to export cleanly across the plug-in boundary.
9. **Deterministic VFS claims table and `nondeterminism` error** [`VFS`] `[31:50]` `[32:24]` `[32:43]` `[33:08]` - **Decision:** Roughly 80% of the VFS crate implements an operation-ordering claims table: as each prompt chain performs I/O, it records read, write, and directory-check claims, and if any concurrent chain makes an overlapping conflicting claim (write-write or read-write), execution halts immediately with a `nondeterminism` error. **Rationale:** Guarantees that every run of a prompt produces identical results regardless of how the harness schedules concurrency.
10. **Fan-out subagent virtual-file isolation** [`VFS`] `[33:20]` `[33:37]` - **Decision:** When a prompt fans out across multiple concurrent subagents (such as 10 research subagents), each subagent must write to its own separate virtual file before a deterministic combine step merges the results. **Rationale:** Separate git worktrees alone do not solve in-memory VFS merge safety; concurrent writes to a shared virtual path violate determinism.
11. **Single shared `Arc` VFS with vended chain-ID `Access`** [`VFS`] `[38:27]` `[38:53]` `[39:13]` - **Decision:** All prompts running in Workshop share a single `Arc`-referenced VFS instance that exposes no direct I/O methods; to touch files, a caller must vend an `Access` token that embeds the calling chain's unique identifier. **Rationale:** Allows the central claims table to track file ownership across both subagent chains within one prompt and separate prompts running simultaneously in Workshop.
12. **Borrowed `Access` lifetime and automatic claim release** [`VFS` / `Plug-ins`] `[35:03]` `[39:31]` `[39:50]` `[40:10]` - **Decision:** Plug-ins receive `Access` strictly as a borrow (`Send` but not `Sync`, non-cloneable and non-forgeable); when the plug-in returns or drops the `Access`, all file claims held by that token are automatically released. **Rationale:** Prevents a plug-in from passing its `Access` to another actor, running unsynchronized parallel operations inside a single borrow, or leaking file locks after a tool call finishes.
13. **Immediate `Access` revocation on cancel or app exit** [`VFS` / `Harness`] `[40:28]` `[40:44]` `[41:04]` - **Decision:** When a user presses stop or exits Workshop, the host revokes active `Access` tokens immediately instead of calling into each running plug-in to unwind; the plug-in discovers the revocation as an error on its next VFS call. **Rationale:** Eliminates shutdown stalls across dozens of active plug-ins so stopping a run or closing the IDE is instantaneous.
14. **Synchronous VFS core and tool-call async boundary** [`VFS` / `Engine`] `[28:05]` `[28:31]` `[34:04]` `[35:39]` `[45:00]` - **Decision:** The Runvil Engine, Lua VM, step loop, and VFS backends are synchronous by design for determinism; the initial plug-in VFS surface ships with synchronous `Access` methods while keeping the overall tool call as the async boundary, leaving room for an additive async surface later. **Rationale:** Because the underlying VFS backends are synchronous, an async `Access` API is only a thread-hop veneer; shipping synchronous first keeps return types simple, avoids extra data structures, and unblocks plug-in development (`bashkit`) immediately (`[36:19]`, `[45:08]`).
15. **Host performer thread-hop placement and cancel ack** [`Harness` / `Plug-ins`] `[37:47]` `[43:00]` - **Decision:** When running a synchronous tool body on a worker thread, the host must wait for the worker to acknowledge before ending the `Access` on cancel, and for Rust-linked packs the thread hop must live in the host's performer future rather than inside the pack. **Rationale:** Prevents an in-flight race condition where a worker thread continues operating on a borrowed `Access` after the host has ended or dropped the cancelled future.

## 3. Engineering & Teaching Principles

20. **Keep agentic components minimal and finishable** `[13:05]` `[13:25]` `[14:57]` `[15:15]` (`stated`, Vinnie) - **When** decomposing an agentic system into architectural layers (such as Engine, Harness, and Plug-ins), **do** define each core layer as the smallest surface whose removal breaks its responsibility and push everything else into outer layers or plug-ins, **because** small isolated components keep tests finite, prevent model confusion during agentic coding, and allow core layers to be declared permanently finished.
21. **Deliberate carefully on hard-to-reverse API boundaries** `[21:16]` `[21:32]` `[22:09]` `[22:27]` (`stated`, Vinnie) - **When** choosing a foundational API signature (such as synchronous vs. asynchronous methods across a plug-in DLL boundary) rather than a tunable constant like `max_concurrency`, **do** gather input from domain experts and evaluate failure modes before committing, **because** changing every function signature later forces rewrites across all tools, logic, and tests.
22. **Never approve jargon-dense AI design advice you cannot evaluate** `[30:22]` `[30:54]` `[36:34]` `[36:51]` (`stated`, Vinnie) - **When** an AI model returns an architectural recommendation packed with unexplained terms ("in-flight hazard", "blocking pool", "host's performer's future"), **do** pause the decision and refuse to ship until every term is understood, **because** approving a consequential design without understanding its rationale surrenders engineering judgment.
23. **Force the model to re-explain with more detail and zero jargon** `[44:06]` `[44:41]` (`demonstrated`, Vinnie) - **When** a model's technical explanation assumes unshared context or uses opaque terminology, **do** prompt it to re-explain for a newcomer to the module using more detail, no jargon, and concrete step-by-step mechanics, **because** plain-language restatement exposes the actual mechanism (such as the key-card and sticky-note claims analogy at `[46:13]`).
24. **Switch the coding agent to Ask mode during design exploration** `[24:09]` (`stated` and `demonstrated`, Vinnie) - **When** discussing architectural trade-offs or hypothetical API changes with an AI coding assistant, **do** switch the assistant into Ask (read-only) mode first, **because** otherwise the agent gets eager and begins modifying code before a decision has been reached.
25. **Ship the simpler synchronous surface when it unblocks parallel team scaling** `[34:04]` `[36:19]` `[36:34]` `[45:00]` (`stated`, Vinnie) - **When** a synchronous API preserves determinism, keeps return types simple, and can be implemented immediately while an async alternative adds cancellation hazards, **do** ship the synchronous API first and leave async as a potential additive surface, **because** getting plug-ins working right away unblocks `bashkit` and lets team members build packs in parallel.
26. **Design cancel and exit paths for immediate user response** `[40:44]` `[41:04]` (`stated`, Vinnie) - **When** designing stop and application-exit handling across many loaded plug-ins, **do** revoke access tokens centrally on the host side rather than waiting for synchronous teardown callbacks in every plug-in, **because** users should never wait on a sluggish stop button or a hanging IDE exit.
27. **Sequester shared credentials into a single boundary process** `[11:23]` `[11:32]` `[11:40]` (`stated`, Vinnie) - **When** multiple local applications, workspaces, or scheduled prompts need third-party API keys, **do** store and attach those keys inside Gateway rather than distributing them to every client harness, **because** keeping secrets in one process minimizes the attack surface.
28. **Cap exposed tool counts to match model capacity** `[6:02]` `[6:19]` `[6:45]` (`stated`, Vinnie) - **When** offering tools to a model inside a prompt, **do** restrict the active tool catalog to only the tools needed (especially restricting 3B-9B models to roughly 3-8 tools), **because** flooding the context with hundreds of tools degrades model tool-selection accuracy.

## 4. Teachable Mental Models

29. **VFS `Access` as a hotel key card with sticky-note claims** `[38:27]` `[38:53]` `[46:13]` `[46:30]` - The shared VFS is a building that no prompt can enter directly. To touch any file, a prompt chain must be vended a borrowed key card (`Access`) stamped with that chain's ID. Every time the key card is swiped to read, write, or list a path, the VFS checks the rulebook, posts a sticky note (a claim) on that path visible to all other chains, and halts with a `nondeterminism` error if two chains' sticky notes conflict. When the key card is returned (dropped), all of its sticky notes come off at once; if the user hits Stop, the front desk deactivates the key card remotely so the next swipe fails immediately.
30. **Why a naked Harness can only psychoanalyze** `[5:06]` `[14:21]` `[14:44]` - A language model by itself only maps text in to text out. A bare Runvil Harness wired to a model with zero plug-ins loaded lets you chat with Claude, but the agent cannot read a file, search the web, or even accept structured user input without the `user_input`, `std`, and `web` plug-in packs.
31. **Async VFS as a worker-thread veneer over synchronous backends** `[28:31]` `[35:15]` `[35:39]` - Because the Lua VM, the step loop, and the underlying VFS storage backends are synchronous and `Access` is `Send` (movable across threads) but not `Sync` (not safe for simultaneous multi-thread access), making `Access` methods `async` does not make the underlying file operations non-blocking; it merely hops the synchronous work onto another thread and wakes a future when finished.
32. **Why Google blocks raw Tokio HTTP fetches** `[8:47]` `[9:13]` - An agent cannot implement web search by firing raw HTTP requests from Tokio at Google, because ad-supported search engines aggressively detect and block automated bot traffic that does not view ads. Reliable agent web search requires a paid search provider API key (such as Brave) managed by Gateway.
33. **Irreducible subtraction test for Engine vs. Harness** `[13:45]` `[14:02]` `[14:21]` - To decide whether a piece of code belongs in the Engine, the Harness, or a Plug-in, apply the subtraction test: if removing it stops the Runvil language from executing at all, it belongs in the Engine; if removing it leaves the language intact but prevents the Engine from talking to the outside world, it belongs in the Harness; if the system still runs without it, it belongs in a Plug-in.
